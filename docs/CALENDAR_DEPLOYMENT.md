# Настройка синхронизации СКТ-225

`Fetch Sarov schedule` запускается каждый час на 17-й минуте UTC. Загрузка PDF, распознавание и проверка идут в одном job с планированием и сверкой календаря. PR и обычный push в `main` выполняют проверки с выключенным календарём. Отчёт публикуется отдельным job с правом `contents: write` в ветку `calendar-sync-reports` по пути `latest.json`. Отчёт также доступен в Job Summary и артефакте `sync-report`.

## Доступ сервисного аккаунта

1. Откройте [Google Cloud Console](https://console.cloud.google.com/projectcreate) и создайте отдельный проект для СКТ-225. В выбранном проекте откройте [Google Calendar API](https://console.cloud.google.com/apis/library/calendar-json.googleapis.com) и нажмите **Enable**.
2. Откройте [IAM & Admin → Service Accounts](https://console.cloud.google.com/iam-admin/serviceaccounts). Выберите **Create service account**, укажите имя, например `skt225-calendar-sync`, и завершите создание без назначения проектных ролей. Скопируйте email созданного аккаунта.
3. В [Google Calendar](https://calendar.google.com/) откройте **Настройки → Настройки моих календарей → Расписание СКТ-225 → Доступ для отдельных пользователей или групп**. Добавьте email сервисного аккаунта с правом **Просмотр всех сведений о мероприятиях**. Проверьте имя, часовой пояс `Europe/Moscow` и ID в разделе **Интеграция календаря**: `f311eb844a8fcb81b18529a77e2ce85057a80d90d467bbe3b60b4202eb586da8@group.calendar.google.com`. Режим записи позднее потребует только **Внесение изменений в мероприятия**. Право управления доступом и делегирование на уровне домена не нужны.
4. Вернитесь в созданный сервисный аккаунт в Google Cloud. Вкладка **Keys → Add key → Create new key → JSON**. Если политика организации блокирует создание ключей, используйте согласованную настройку федерации с администратором. Не ослабляйте политику ради этого репозитория.
5. Откройте [Settings → Secrets and variables → Actions](https://github.com/retr0-pm/sarov-schedule-skt225/settings/secrets/actions) → **New repository secret**. Укажите имя `SKT225_GOOGLE_SERVICE_ACCOUNT_JSON` и вставьте содержимое JSON непосредственно в форму GitHub. После сохранения удалите локальную копию ключа безопасным способом. Если ключ был раскрыт, отзовите его в Google Cloud и создайте новый.

Для `dry-run` модуль запрашивает scope `calendar.events.readonly`, для `apply` — `calendar.events`. Права самого сервисного аккаунта ограничены ACL одного календаря. Сетевой клиент использует фиксированный Calendar ID и фиксированный адрес Google API. [Документация Google по scope](https://developers.google.com/workspace/calendar/api/auth)

Workload Identity Federation устраняет долгоживущий ключ. Для неё потребуется настроить доверие к GitHub OIDC с ограничением по ID репозитория и ветке `main`, разрешить этому субъекту impersonation сервисного аккаунта и выдать короткоживущий токен со scope Calendar. Начальный workflow использует ключ в GitHub Actions Secret и не получает OIDC-права. Федерация потребует отдельной проверки вызова Calendar API с таким токеном. [Настройка федерации и impersonation](https://github.com/google-github-actions/auth)

## Проверка и активация

1. Откройте [Actions → Fetch Sarov schedule](https://github.com/retr0-pm/sarov-schedule-skt225/actions/workflows/fetch.yml) → **Run workflow**, выберите `main` и `calendar_mode=dry-run`. Отчёт должен иметь `validation=verified`, `status=dry_run` и точный список `planned`. При `error` или `conflict` устраните причину.
2. После проверки плана измените право сервисного аккаунта в календаре на **Внесение изменений в мероприятия** и задайте `SKT225_SYNC_MODE=apply`. Это разрешает создание, обновление и удаление занятий по расписанию и при ручном запуске `apply`. Ручной `dry-run` остаётся доступным. [Переменные GitHub Actions](https://github.com/retr0-pm/sarov-schedule-skt225/settings/variables/actions)

Для немедленной приостановки записи задайте `SKT225_SYNC_MODE=off`. Дождитесь завершения активного job. Уже выполненные операции остаются в календаре, а следующий запуск восстанавливает состояние по маркерам.

Если первый `dry-run` возвращает `google_calendar_api_disabled`, включите [Google Calendar API](https://console.cloud.google.com/apis/library/calendar-json.googleapis.com) в проекте, который выпустил ключ сервисного аккаунта. При `google_calendar_permission_insufficient`, `google_calendar_access_forbidden` или `calendar_http_404` проверьте, что email в ACL календаря совпадает с `client_email` используемого ключа и получил право видеть все сведения о мероприятиях. После изменения повторите `dry-run`. Отчёт публикует только фиксированные коды диагностики.

## Идентификация и повторные запуски

Существующие события сопоставляются по шести строкам `key=value` в описании. Дополнительные служебные строки прежних версий можно сохранить. При сравнении учитываются фактические начало и конец, заголовок, аудитория, преподаватель и вид занятия. SHA PDF пишется при создании или содержательном обновлении. Изменение только PDF, отпечатка манифеста или времени формирования артефакта не вызывает записи.

Однозначный перенос на расстояние до 14 дней сопоставляется по серии и предмету. Для обновления существующего события при замене преподавателя, формы занятия или предмета требуются валидные маркеры владения и однозначное сопоставление. Уже начавшиеся занятия сохраняются.

Новые ID вычисляются из `source_id` в допустимом Google формате. При HTTP 409 клиент читает события по ID и принимает результат только при полном совпадении. Обновления и удаления защищены `If-Match`. Повторяются только безопасные чтения с ограниченным ожиданием при 429, 5xx и сетевых сбоях. После неоднозначного результата записи следующая операция откладывается до нового чтения. В конце `apply` планировщик повторно сверяет календарь. Сериализация в Actions охватывает запуски этого workflow. Внешнего писателя она не блокирует, а Google отдельно оговаривает возможные коллизии клиентских ID в своей распределённой инфраструктуре. [Формат ID Google Calendar](https://developers.google.com/workspace/calendar/api/v3/reference/events#resource)

Если проверенное расписание однозначно заменяет одно занятие в том же временном слоте, синхронизация обновляет существующее событие. При нескольких кандидатах она создаёт новые занятия и удаляет устаревшие после проверки принадлежности событий и покрытия недели. Если занятие пропало из проверенной недели, соответствующее будущее событие удаляется автоматически. При неполном комплекте PDF или неоднозначном распознавании календарь остаётся в прежнем состоянии.

Если единственный участник старого события совпадает с его создателем, а организатором выступает целевой календарь, обновление сохраняет запись об участии. Событие с таким участником может быть удалено при отмене занятия. События с другими гостями или конференциями блокируют запись.

Отчёт содержит числа, публичные названия из PDF для созданий и обновлений, а также дату и время для отмен. В отчёте отсутствуют идентификаторы Google событий, описания из календаря и ответы провайдера. Ветка отчётов хранит историю отчётов.
