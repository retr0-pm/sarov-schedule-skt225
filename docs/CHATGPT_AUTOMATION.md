# Требования к автоматизации ChatGPT для СКТ-225

Этот документ описывает отдельного потребителя GitHub Actions Artifact. Код данного репозитория не обращается к Google Календарю и не подтверждает календарную синхронизацию.

## Источник и область обработки

- Репозиторий: `retr0-pm/sarov-schedule-skt225`.
- Ветка: `main`.
- Workflow: `Fetch Sarov schedule`.
- Имя артефакта: `sarov-schedule`.
- Группа: **СКТ-225**, второй курс.
- Часовой пояс событий: **`Europe/Moscow`**.
- Версия правил: **`skt225-v3`**.

Использовать только последний завершённый успешный run. Артефакт самодостаточен и содержит `manifest.json`, все PDF семестра, `schedule.json` и `ambiguities.json`.

## Что проверяет регулярная задача

ChatGPT не должен повторно интерпретировать сложную геометрию PDF при каждом запуске. Геометрическое распознавание выполняет GitHub Actions. Потребитель обязан:

1. Проверить, что run успешен, артефакт не истёк и называется точно `sarov-schedule`.
2. Проверить состав и SHA-256 PDF по `manifest.json`.
3. Проверить `manifest_fingerprint`, `schema_version`, `rules_version`, группу и часовой пояс в `schedule.json`.
4. Проверить уникальность `source_id`, ссылки событий на известные PDF и согласованность сводных счётчиков.
5. Прочитать `recognition.status`, статусы недель и `safe_for_deletions` до планирования календарных операций.

PDF остаются источником для аудита. Если структурированные данные не проходят проверку, нельзя молча переходить к самостоятельному распознаванию и выдавать его за проверенный результат.

## Правила `skt225-v3`

В `schedule.json` уже применены правила фильтрации. Для проверки ожидаемой версии зафиксированы следующие правила:

- исключаются «Особенности нейронных сетей» и «Особенности практического использования нейронных сетей»;
- исключаются «Решение нелинейных дифференциальных уравнений» и «Нелинейные дифференциальные уравнения»;
- из всех спецсеминаров остаётся только «Параллельные вычисления и анализ алгоритмов»;
- обычные предметы не исключаются из-за отдельных совпадающих слов.

Если `rules_version` отличается от поддерживаемой, остановить синхронизацию и запросить обновление правил потребителя.

## Идентификация событий и переносов

Каждое событие содержит:

- `source_id` — идентификатор появления серии в конкретной учебной неделе, не основанный только на дате и времени;
- `series_id` — переносоустойчивый кандидат, основанный на группе, предмете, преподавателе и виде занятия;
- `source_locator` — диагностическое положение в PDF;
- `source_pdf_sha256` и `week_id` — происхождение и область проверки.

Сначала сопоставлять по `source_id`. Если он изменился, разрешается рассмотреть `series_id` как кандидата на перенос только при единственном однозначном старом и новом событии в ограниченном диапазоне. При нескольких кандидатах перенос считается неоднозначным: не создавать автоматическую связь и не удалять старое событие.

## Безопасная синхронизация

1. Для каждой недели сопоставить `source_pdf_sha256` и `rules_version` с защищённым состоянием автоматизации.
2. Повторно обработать неделю, если изменился PDF, версия правил или прошлый календарный статус не был `verified`. Совпадение SHA-256 не доказывает синхронизацию календаря.
3. Работать только с разрешённым временным диапазоном и интерпретировать время в `Europe/Moscow`.
4. Перед изменениями прочитать все управляемые события недели и построить план `create/update/delete/no-op/conflict`.
5. Помечать события private extended property `managed_by=sarov-schedule-skt225` и сохранять `source_id`, `series_id`, `week_id`, `rules_version` и SHA-256 PDF. Если extended properties недоступны, использовать однозначный машинный маркер в описании.
6. Не изменять пользовательские события и события других систем. Сходство заголовка не передаёт владение этой автоматизации.
7. Создавать отсутствующие события и обновлять однозначные изменения без дубликатов.
8. Удалять отсутствующее событие только когда конкретная неделя имеет `status=verified`, `safe_for_deletions=true`, её PDF и структурированные данные проверены, а событие принадлежит этой системе.
9. При `ambiguous`, `error`, неполном диапазоне или неоднозначном переносе сохранять существующие события и сообщать о конфликте.
10. После записи повторно прочитать календарь недели и проверить ожидаемое количество и поля событий.
11. Только после фактической проверки календаря установить `calendar_sync.status="verified"`.

Статус распознавания GitHub и статус календарной синхронизации независимы. Даже полностью проверенный `schedule.json` не означает, что Google Calendar уже обновлён.

## Минимальное состояние недели

```json
{
  "week_id": "2026-11-23/2026-11-28",
  "pdf_sha256": "…",
  "manifest_fingerprint": "…",
  "rules_version": "skt225-v3",
  "recognition": {
    "status": "verified",
    "safe_for_deletions": true,
    "checked_at": "2026-11-22T12:00:00Z"
  },
  "calendar_sync": {
    "status": "pending",
    "last_success_at": null,
    "last_error": null,
    "expected_events": 12,
    "verified_events": 0
  }
}
```

Допустимые календарные статусы: `pending`, `verified`, `error`, `ambiguous`. GitHub Actions и загрузчик PDF не вправе самостоятельно устанавливать календарный статус `verified`.

## Предыдущие данные

Проверенный `schedule.json` прошлого запуска можно хранить как baseline для сравнения. Он не считается актуальным автоматически. Если текущая неделя неоднозначна, предыдущие данные разрешено показать оператору как справочные, но нельзя подменять ими текущий результат или на их основании выполнять удаления.
